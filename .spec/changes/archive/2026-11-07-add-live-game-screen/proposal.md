# 变更：游戏画面实时送到手机

## 动机

三个自动化引擎（MAA / BetterGI / M7A）本质上都靠「截图 + OCR」驱动，游戏画面一直存在，只是从来没送到手机上。现在 APP 只能看文字状态和日志，点了「开始」之后完全看不到电脑上正在发生什么，卡住了也不知道卡在哪一步。

这是当前体验上最大的缺口：任务跑起来之后，用户对电脑的唯一感知是几行日志。

## 范围

在范围内：

- 服务端按需截取游戏窗口，三种游戏统一走 Windows 窗口截图（BitBlt），复用现有窗口定位能力
- `GET /api/screen/{game}` 返回 JPEG，带 quality 参数与明确的错误码
- 性能预算：单张处理 < 100ms，1080p 画面 JPEG ≤ 300KB
- 截图过程不激活窗口、不抢焦点、不影响正在运行的任务
- APP 每个游戏页增加「画面」区域：运行中自动刷新（1~2 秒一张）、未运行时停止自动刷新但保留手动刷新、保留最后一张并标记旧快照、显示截图时间与失败原因

不在范围内：

- 录制视频、回放、历史截图归档
- 多游戏同时观看（一次只显示当前游戏页的画面）
- 音频
- 画面识别（OCR / 模板匹配）与基于画面的自动决策
- 服务端主动推流（WebSocket 推图）；本次仍由客户端按需拉取

## 方法

服务端新增窗口定位（按游戏进程找主窗口）与截图管线（BitBlt → Pillow 缩放 → JPEG 编码），封装成一个受全局锁保护的同步函数，由 FastAPI 的同步路由在线程池里调用，避免阻塞事件循环。截图只读窗口 DC，不做任何窗口激活/移动操作。

APP 端复用现有 `ApiClient`（带 token 的 OkHttp）新增二进制下载方法，在 `AppViewModel` 里维护每个游戏的画面状态与刷新任务：任务运行中每 1.5 秒拉一张，任务结束、切页、断开连接、APP 进后台时停止。图片以 `ImageBitmap` 直接解码显示，不落盘。

性能上靠两件事成立：BitBlt 抓窗口（实测 3.9ms，1294×829）与「宽 1280 上限 + quality 70」的编码预算（实测约 20ms）。全黑检测用缩小后采样的方式，避免把全黑图当成成功结果。
