# 变更：任务生命周期重构与两端性能优化

## 动机

三个问题咬在一起，但根子是同一个：**任务状态的判定方式是错的，而代码结构让这个错误很难被看见。**

### 1. 任务「完了却不算完」——三个引擎各有各的病

**星铁**：实测证据（2026-11-08 02:08 那次编排）：

- 三月七自己的运行记录 `logs/runs/20261108-020836-928f.json`：
  `status: "success"`、`exit_code: 0`、`02:08:36 → 02:31:02`，差分宇宙用时 20 分 16 秒。
- 我们服务端的任务记录 `c729cb1e88d1`：
  `state: "timeout"`、时长 **14724 秒（4 小时 5 分）**、`error: "超过 1800 秒未结束"`、
  结束时间 `06:13:59`。

任务 22 分钟就成功了，我们却把它显示成 4 小时超时。原因是
`subprocess.run(capture_output=True, timeout=1800)`：捕获的管道句柄被引擎派生的进程
（这里是被 m7a 启动、继承句柄的 `StarRail.exe`）持有，管道不 EOF 就一直等；
1800 秒触发 `TimeoutExpired` 后 kill 父进程，而 Windows 上随后的第二次 `communicate()`
没有超时保护，于是又干等了三个多小时，直到游戏被关掉才返回。

连带后果：因为一直不进入终态，任务结束后的自动清理（关闭游戏释放内存）也就一直没执行。

还有一类会真的挂死的：11-07 23:44 那次游戏窗口消失后，引擎每秒重复
「截图失败：没有找到游戏窗口」，永不退出，只能等我们 1800 秒后强杀。

**而 m7a 早就提供了正确的接口**：`--status --json`（含 `active_run` / `recent_runs`）、
`--detach`、`--control <run_id> stop`、退出码 6 表示被停止。我们一个都没用上。

**原神**：判定标志压根写错了。代码里等的是 `一条龙.*完成` 和 `正在关闭游戏和软件`，
而 BetterGI 实际打印的是 **「一条龙和配置组任务结束」**（`OneDragonFlowViewModel`）。

- `better-genshin-impact20261106.log`：`一条龙和配置组任务结束` 出现 1 次，
  现有两个正则匹配 **0 次**；11-05、11-07 的日志同样 0 次。
- 于是进程退出后必然走到 `finish(FAILED, "BetterGI 退出但未检测到完成标志")`
  ——**原神任务只要跑完就会被判失败**。
- 更糟的是进程退出分支拿 `run.log_tail[-60:]` 去匹配，这个窗口会跨运行取到上一次的内容，
  哪天真的匹配上了，也可能是上一次的假阳性。

**方舟**：判断链路最健康（MAA 主动上报 `SUCCESS`），但没用上官方给的状态接口，还有三个毛病：
超时固定 3600 秒不分档；只要 MAA 还在轮询就算「活着」，任务卡住也只能干等一小时；
`on_report` 直接改任务终态，绕过了状态机。

**查源码才发现**：MAA 的远程控制协议里有 `HeartBeat` 任务类型，
执行后回报的 `payload` 就是**当前正在执行的任务 id**（空闲为空字符串）
（`src/MaaWpfGui/Services/RemoteControl/RemoteControlService.cs`：`payload = _currentSequentialTaskId`）。
也就是说「任务还在不在跑」有官方答案，我们却在打算靠读 `asst.log` 有没有变胖来猜。

**原神**：查了源码，你装的 0.66.0 **没有任何对外接口**（没有 `ExternalAccess` 配置、
目录里也没有 Kestrel/AspNetCore 依赖）。较新版本才提供 loopback 的
`GET /api/v1/health` 与 `ws://127.0.0.1:30648/ws/v1/logs` 实时日志，
而且文档写得很清楚——「不提供任务启动、停止等业务控制能力」，默认还是关的。
所以原神只能读日志，那就更要把完成标志写对。

还有一类三个引擎都会中招的：**把「有日志输出」当成「有进展」**。
原神那边只要读到任何一行就刷新进展计时，引擎若每秒刷同一行，卡死检测就永远不会触发。

**而 m7a 早就提供了正确的接口**（见上）。

### 2. 代码结构

- 服务端 5322 行 / 31 文件，`api/tasks.py` 一个文件同时做前置检查、执行、停止、清理；
  引擎适配器三套写法（m7a 阻塞式、BetterGI 轮询日志、MAA 提交+watch），彼此不一致。
- 桌面端 `qt_ui.py` 1278 行；手机端 `Screens.kt` 1321 行、`ChainScreen.kt` 1138 行、
  `AppViewModel.kt` 789 行。
- 没有明确的依赖方向：`api` 直接调引擎、引擎反向引用编排状态。

### 3. 内存与性能

- 2026-11-08 00:47 三月七日志里的实锤：`OpenCV Insufficient memory,
  Failed to allocate 49838424 bytes` —— 当时机器内存被挤爆（MuMu 一项就占十几 GB）。
- 电脑端常驻 132MB（桌面端与服务端同进程），包体 97MB（PySide6 50MB、PIL 12.9MB、
  swagger 8.2MB）。
- 手机端：任务时 3 秒、空闲 5 秒轮询，而 WebSocket 通道其实已经实现却没被用起来。

## 范围

在范围内：

- **任务生命周期（三个引擎一起）**：
  - 星铁：`--detach` 取 run_id → 轮询运行记录判定 → 超时/卡死用 `--control stop` 优雅停止；
    启动与等待不再捕获管道。
  - 原神：完成标志修正为「一条龙和配置组任务结束」，并且只匹配**本次运行**的日志区间。
  - 方舟：改用官方远程控制协议里的 `HeartBeat`（回报当前正在执行的任务 id，空闲为空串）判活，
    不再观察日志文件；加「15 秒无轮询 = 离线」与「心跳停在同一个任务 10 分钟 = 卡死」两条判据；
    回报结果统一交回状态机。
  - 三者共用：**按「距最后一次有效进展」判异常，不按总时长**（慢机器跑 35 分钟不该被杀）；
    日志增量读文件、反刷屏的进展判定、进度展示（阶段 x/y、任务 i/n）、停止 60 秒内收敛。
- **服务端分层重构**：`api` / `core` / `engine` / `platform` 四层，依赖只能自上而下；
  三个引擎适配器统一成一个接口；任务状态只由 `core` 的状态机维护。
- **桌面端**：`qt_ui.py` 按页面拆分；后台采集与界面解耦；内存优化。
- **手机端**：推送优先、轮询兜底；页面按职责拆分；位图与内存约束。
- **性能预算**：电脑端空闲 ≤ 120MB、任务期间增量 ≤ 60MB、空闲 CPU ≤ 单核 1%；
  手机端 ≤ 200MB 且只留一张位图。都写成可命令复现的测量口径。
- **工作区清理**：清掉临时构建产物与旧打包目录，保留可重新生成的交付物。

不在范围内：

- **不改三个引擎本身**：MAA / BetterGI / 三月七的安装方式、配置格式、升级策略都不动。
- **不改通信协议语义**：HTTP 路径、字段、鉴权方式保持兼容，老版本 APP 仍能连。
- **不做定时/周期任务**：上一轮已明确排除，这次仍不做。
- **不改界面视觉设计**：只动结构与性能，配色、布局、文案不重做。
- **不拆进程**：桌面端与服务端仍同进程，除非预算实测达不到再单独评估。
- **不引入重的运行时依赖**：不新增 psutil / numpy 之类；测量用系统自带命令。

## 方法

1. **先修判定，再谈重构**。给引擎适配器定一个统一接口
   （能力清单 / 前置检查 / 启动 / 轮询 / 停止 / 清理），把 m7a 改成
   `--detach` 拿 run_id → 轮询运行记录 → 读日志文件增量 → 超时用 `--control stop`
   优雅停止。所有引擎子进程一律以 `DEVNULL` 启动，绝不捕获管道。
2. **状态机搬到 `core`**。任务与链的状态、终态收敛、广播只在一个地方发生；
   适配器只上报事件。这样「什么时候算结束」只写一次。
3. **按层搬代码**，每搬一个模块就补它自己的测试；拆文件时以职责为界，
   顺手把超过 300 行的文件拆到线内。
4. **性能按预算做，不按感觉做**。先测基线（内存、CPU、截图耗时、轮询次数），
   再逐项优化（懒加载、复用缓冲、关 access log、Qt 模块裁剪、推送替代轮询），
   最后用同一套命令复测对比。
5. **每一步都能单独验证**：生命周期用真跑一次星铁验证；内存用 `Get-Process`；
   规模与依赖用脚本检查。
